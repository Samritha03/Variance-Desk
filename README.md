# Variance Desk (Grounded Variance Explainer)

A web app that explains monthly budget-vs-actual variances for a finance team, built as a RAG agent with a verification layer.

> The code does the math. An agent finds the evidence and must quote it. A verifier checks every figure. A person signs off.

All data is fictional (generated by scripts in `data/`). Backend: FastAPI + the Python engine in `gve/`. Frontend: React (Vite) in `web/`.

## The problem

A finance team closes the month and has to explain, for the CFO, why numbers moved against budget. Today an analyst digs through ledgers, invoices and email threads, then writes it up. An AI draft is only useful if it cannot put a wrong number or an invented reason in front of a CFO.

## The app

| Page | What it does |
|---|---|
| Overview | KPIs for the month and a four-step workflow with live status |
| Variances | Run the agent; per line: numbers, verdict, quoted evidence (click to open the source with the quote highlighted), a step-by-step trace of the agent's tool calls, accept or write your own reason |
| Commentary | Draft, edit, and watch the verifier re-check every change live. "Plant 3 errors" shows it catching a wrong number, a flipped direction and an invented cause |
| Data checks | Ledger pre-flight (duplicates, unmapped accounts, sign flips, gaps, spikes) and CSV upload |

## How it works

| Step | What happens | Model involved? |
|---|---|---|
| 1. Pre-flight | Flags missing months, unmapped accounts, duplicates, sign reversals, spikes | No |
| 2. Variance math | Variance $ and %, favorable or not, materiality thresholds | No |
| 3. Investigate | Agent searches documents and ledger transactions for the reason behind each material line, then records a finding with citations | Yes (agent) |
| 4. Analyst context | A person adds reasons. A note always overrides the agent | Human |
| 5. Draft | Prose written from a table of pre-computed facts, plus any accepted, verified suggestions | Yes (drafter) |
| 6. Verify | Every $ and % matches a computed value; direction and favorability match; a cause is allowed only with an analyst note or a verified suggestion; cited source ids must belong to that line | No |
| 7. Approve | Locked until verification is clean | Human |

### The agent (step 3)

- **Retrieval:** hybrid. BM25 (keyword) and embeddings each rank the chunks, and reciprocal rank fusion merges the two lists. A date-window metadata filter applies first. `gve/retrieval.py` holds `Retriever(mode='bm25'|'dense'|'hybrid')` and a pluggable embedder.
- **Tools:** `search_documents`, `get_transactions`, and `record_finding`. Code runs the tools; the model chooses what to look at. The ledger reconciles to the GL to the cent.
- **Loop:** one tool-use loop per variance line, with a step limit, so a line can only cite what it retrieved itself.
- **Grounding check (`ground()` in `gve/agent.py`):** a finding is downgraded to `unverified` unless every cited source was retrieved in that run, every document quote appears word for word in the retrieved text, and every $ and % in the explanation traces to a cited quote, a cited transaction or the computed variance.
- **Honest "no":** one variance (Engineering salaries) has no explanation anywhere in the files, and two documents are traps (a hire who starts next month, a merit memo from last December). `no_evidence` is a correct answer.

## Evaluation

`python -m gve.evals` scores against `data/corpus_key.json`: which documents truly explain each variance, and which line has no explanation at all.

**Retrieval alone** (top 4, date filter on; 12 gold documents; 20 paraphrased queries a real agent might write):

| Search | Key queries | Paraphrased queries |
|---|---|---|
| Keyword (BM25) | 11/12 | 25/48 |
| Embeddings | 12/12 | 33/48 |
| Hybrid (BM25 + embeddings, rank fusion) | 12/12 | 32/48 |

Hybrid clearly beats keyword-only on reworded queries. It does **not** beat embeddings alone here, and the embedder is the local LSA model (below), so treat this as evidence for the method, not a benchmark. The date filter keeps last year's audit invoice out of the results (1 wrong-period document appears without it).

**End to end** (`baseline` is a one-shot keyword lookup, the floor the agent must beat): right document 4/5, cause actually stated 0/5, false attribution 0/1. **The Claude agent has not been run by me**; no API key was available while building. `python -m gve.evals --claude` adds its rows.

### Embeddings

The default embedder (`LSAEmbedder`) is TF-IDF over words and character n-grams reduced with SVD, fitted on the document set. It runs offline with no downloads, but it is **not a neural model**. For production set `GVE_EMBEDDER=fastembed` (after `pip install fastembed`; downloads BAAI/bge-small-en-v1.5 once) or implement the two-method `fit/encode` interface for a hosted embeddings API.

## Added in v4

- **Benchmark (36 cases).** `python -m gve.bench` (add `--claude` with `ANTHROPIC_API_KEY`). 28 variances with a real cause, each with two true documents plus decoys (last year's version, an unapproved proposal, a quote-only estimate), and 8 with no real cause. Data is generated by `data/bench/generate_bench.py`. Results only cover search and the keyword baseline until you run it with a key; **the Claude agent has not been measured**.
- **Documents.** Upload .txt, .md, .eml or text-based .pdf (no OCR). The date is read from the file or you enter it; a file with no date is refused, because the search filters by date. Uploads are held in memory per browser (header `X-GVE-Session`), capped at 50, and lost on restart. They are searched together with the sample documents, so only the sample company's investigation uses them.
- **Account mapping.** `python -m gve.mapping` (add `--claude` with a key). 28-account standard chart, 3 fictional entities (64 accounts) with traps: same code with a different meaning, German names, vague names, accounts with no home. The mapper proposes; only confident proposals auto-apply, the rest go to review, and approved decisions become rules. Baseline (name similarity, thresholds set once and not tuned): 38/64 right, 23 auto-applied all correct, every wrong proposal sent to review. **The Claude mapper has not been run.**
- Light, Liv-Data-style palette (aubergine #280949 / #5F378B).

Not done: persistence, auth, an audit trail, OCR, neural embeddings by default (LSA is the default; `GVE_EMBEDDER=fastembed` for bge-small), a built and tested Docker image.

## Running the AI agent (Claude or Gemini)

The agent, the follow-up questions and the mapper run on either model. Set one key; no code changes.

```
export GEMINI_API_KEY="..."        # free key from aistudio.google.com   (or ANTHROPIC_API_KEY for Claude)
python3 -m gve.llm                 # one tiny call: checks the key, the model name and tool calling
python3 -m gve.mapping --llm       # mapper on the 64-account answer key
python3 -m gve.bench --llm --limit 10   # agent on 10 of 36 cases (hybrid search only); drop --limit for all
python3 -m gve.evals --llm         # the 6-line demo
```

Results describe whichever model ran (the table names it). Gemini defaults to `gemini-3.8-flash`; change with `GVE_GEMINI_MODEL`. Calls are spaced 4 s apart for free-tier limits (`GVE_LLM_MIN_INTERVAL`) and rate-limit errors are retried. Free-tier daily limits can stop a long run: use `--limit`. The AI writer on the Commentary page uses the same key (Claude or Gemini).

Everything works without a key (keyword baseline, template writer). ## Deploy

The app deploys two ways:

- **Simplest: one container.** `docker build -f docker/Dockerfile -t variance-desk .` (run from the project root) then run it on Render, Railway, Fly.io or Cloud Run. Add `ANTHROPIC_API_KEY` as a secret. The container serves the API and the React app together.
- **Split: Vercel + API host.** Deploy `web/` to Vercel with `VITE_API_URL=https://your-api-host`; deploy the API from the Dockerfile; set `GVE_CORS=https://your-app.vercel.app` on the API. Long agent runs stream from the API host, not Vercel functions.

The API keeps uploaded files in memory only (20 most recent), which is fine for a demo; add storage and auth before real client data.

## Known limits

- The Claude agent path is covered by tests with a scripted fake model, not by a live run.
- The grounding check proves a quote exists and a figure traces back. It cannot prove the quote supports the conclusion; that is what the eval and the human reviewer are for.
- A verified suggestion's wording is checked for figures and source ids, not for meaning.
- Documents and ledger exist only for the sample company; uploaded GL files get pre-flight, variances and drafting, but no investigation.
- Single month, single entity, no currency handling, no auth, no persistence. Thresholds are defaults, not tuned to a client.

## Tuning log

- **2026-10-22, embedding size.** The local embedder (LSA) used 48 dimensions. On the paraphrased benchmark queries, 16 to 24 dimensions did clearly better. I chose by looking at half the cases and checked on the other half (hybrid recall@4 on that held-out half: 43% with 48 dimensions, 62 to 65% with 16 to 24). Default is now 20. Over all 36 cases, hybrid recall on paraphrased queries went from 49% to 64%; keyword search is unchanged at 43%. Caveat: the benchmark and corpus are synthetic and small, and the best size depends on corpus size, so treat this as a sensible default, not a general result. The Gemini agent numbers in `data/measured.json` were produced before this change and have not been re-run.

## Held-out check

`python -m gve.holdout` runs retrieval on queries that were not used to choose any setting: 30 hand-written rewordings of each case's real reason, plus invoice-number queries generated from the documents (the answer is every document that contains the number). Add your own queries to `data/bench/holdout.json` under `extra` to make it harder. Do not tune against it. First result (embedding size 20, recall@4): rewordings keyword 82%, embeddings 88%, hybrid 85%; invoice numbers keyword 100%, embeddings 75%, hybrid 100%. The rewordings carry more specific detail than the benchmark's generic paraphrases, so they are easier, not a harder test.
